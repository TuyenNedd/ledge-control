# Settings UI, onboarding, and build tooling for Ledge

Adds a SwiftUI Settings window (three tabs: Gesture, Behavior, About) hosted via NSHostingController, a three-page first-launch onboarding flow that polls Accessibility permission live and shows step-count feedback, a menu bar icon tint highlight during active gestures, a configurable codesigning identity with certificate guide, and a `make reinstall` target. The SettingsViewModel uses `@Observable` with `didSet` hooks to write through to `Preferences` and call `applyPreferences()` immediately on every change. Watch for: timer leaks in OnboardingView that never invalidate (confirmed), the onboarding `closeWindow` wiring that reconstructs the entire SwiftUI view tree after init (confirmed), and a potential high-frequency `applyPreferences()` call during slider dragging (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

Every `didSet` on the SettingsViewModel writes to UserDefaults and triggers `applyPreferences()`, which means slider dragging fires engine reconfiguration on every frame (~60 Hz). Tolerable for this app's lightweight apply path, but architecturally noisy.

The onboarding flow runs two `Timer.scheduledTimer` instances (one per page) that are never invalidated. After the window closes, both timers continue firing indefinitely on the main run loop. This violates the clean-shutdown principle the rest of the codebase follows.

The `OnboardingWindow` init creates an `OnboardingView`, assigns it to the hosting controller, then immediately replaces `hostingController.rootView` with a second `OnboardingView` to wire the `closeWindow` closure. This reconstructs the view tree and is fragile if `onAppear` side effects are ever added.

The menu bar highlight uses a single `onEngagementChanged` closure on `GestureController` — a single-subscriber slot that a second consumer would silently overwrite.

The Makefile defaults `SIGNING_IDENTITY` to `"Ledge Dev"`, which requires following `docs/CERTIFICATE.md` first. A fresh clone will fail `make app` unless the developer either reads the guide or knows to pass `SIGNING_IDENTITY="-"`.

<summary>Issues (5)</summary>

1. **Timer leak in onboarding** — `startAccessibilityPolling()` and `startStepPolling()` create `Timer.scheduledTimer` instances that are never invalidated. Store timer references and invalidate on window close or use `Timer.publish` with `.onReceive`.
2. **Double view-tree construction in OnboardingWindow** — The hosting controller's `rootView` is replaced immediately after assignment to wire the close closure. Use an `@Observable` coordinator or a closure property that can be set post-init instead of rebuilding the whole view.
3. **Slider fires applyPreferences() per frame** — Every `didSet` on `edgeBandWidth` calls through to `GestureEngine.settings =` on every drag frame. Consider debouncing or deferring the apply to `onEditingChanged`.
4. **Single-slot engagement callback** — `GestureController.onEngagementChanged` is a single closure, not a multi-subscriber mechanism. A second consumer would silently overwrite the menu bar's handler.
5. **Onboarding shows before controller.start()** — The onboarding window is shown before `controller.start()` is called. If `start()` fails (permission denied), the user sees a "Try It" page with a forever-zero step counter behind the permission alert.

## Timer lifecycle in OnboardingView

`startAccessibilityPolling()` and `startStepPolling()` each call `Timer.scheduledTimer(withTimeInterval:repeats:)` and discard the return value. The timers are scheduled on the main run loop and will fire indefinitely — there is no `onDisappear` or invalidation path. The comment in the code acknowledges this ("A more robust approach would use `.onReceive` with a `Timer.publish`") but ships the leaking version.

After the user clicks "Get Started" and the window closes, two timers continue firing. The step-count timer captures `stepCountProvider`, which captures `[weak controller]` — weak, so the controller itself isn't leaked, but the timer's closure allocation and run-loop entry remain.

The fix: switch to `.onReceive` which SwiftUI cancels automatically when the view leaves the hierarchy:

```swift
.onReceive(Timer.publish(every: 1.0, on: .main, in: .common).autoconnect()) { _ in
    isAccessibilityGranted = Permissions.isTrusted()
}
```

## OnboardingWindow double-init pattern

```swift
// First construction (closeWindow is a no-op):
let onboardingView = OnboardingView(..., closeWindow: {})
let hostingController = NSHostingController(rootView: onboardingView)
// ...window setup...

// Second construction (closeWindow wired to window.close()):
hostingController.rootView = OnboardingView(..., closeWindow: { windowRef?.close() })
```

This creates the entire `OnboardingView` body twice during init. It's fragile — if `OnboardingView` ever acquires `onAppear` side effects, they'll fire on the discarded first instance. A coordinator pattern (an `@Observable class OnboardingCoordinator` with a `close()` method injected into the view) would avoid the double construction entirely.

## SettingsViewModel apply-on-every-drag

```swift
var edgeBandWidth: Double {
    didSet { writeGestureSettings(); applyPreferencesClosure() }
}
```

During a slider drag, SwiftUI sends a new value on every frame. Each invocation writes seven doubles to UserDefaults and calls `applyPreferences()`, which sets `engine.settings` (a struct copy) and calls `engine.setEnabled()`. The `setEnabled` path can emit events if it transitions from disabled to enabled, though in steady-state it returns an empty array.

A `Slider(..., onEditingChanged: { editing in if !editing { apply() } })` pattern would batch the write to drag-end while still allowing the preview to update live via the binding.

## Single-slot engagement callback

`GestureController.onEngagementChanged` is a stored `((Bool) -> Void)?`, set once by `MenuBarController`. If a HUD, sound effect, or haptic feedback ever needs the same engagement signal, it would overwrite the menu bar's handler. The engagement state is already exposed via `engagedControl`, so consumers could poll, but the real-time callback is what makes the icon highlight responsive.

## Onboarding ordering relative to tap start

```swift
if !preferences.hasCompletedOnboarding {
    onboarding.show()  // ← window visible, page 3 has step counter
}

if !controller.start() {  // ← tap created here
    presentPermissionAlert(...)
}
```

If `start()` returns `false` (permission denied), the user sees page 3 ("Try It") with a step counter that will never increment, while the permission alert appears on top. The onboarding remains open behind it. Moving `onboarding.show()` after `controller.start()` (or conditionally skipping page 3 when permission is denied) would avoid the dead-UI scenario.

## Codesigning default

The `SIGNING_IDENTITY` variable defaults to `"Ledge Dev"` — a name that only exists after following `docs/CERTIFICATE.md`. The previous default was ad-hoc (`--sign -`), which always works. The Makefile prints a hint (`# Ad-hoc: make app SIGNING_IDENTITY="-"`), but the failure mode is a codesign error with no direct pointer to the guide. Consider having the Makefile check `security find-identity` and print a diagnostic if the identity is missing.
